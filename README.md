# Gate5 提出物

IT資産管理システム「PC貸出処理」(正常系だけの仕様書から例外系を補完して実装)
技術構成:Node.js + Express + SQLite(better-sqlite3)+ EJS(Gate1 と同じ)

## 1. 起動手順

前提:Node.js 18 以上(動作確認は v24)

```bash
npm install      # 依存パッケージのインストール
npm run seed     # DBを初期状態に戻す(初回は npm start 時に自動作成されるので省略可)
npm start        # http://localhost:3000 で起動
npm test         # 例外系の自動テスト(43 件)
```

| コマンド | 内容 |
|---|---|
| `npm start` | アプリ起動 |
| `npm run seed` | DB(data.sqlite)を削除し、シードデータで作り直す |
| `npm run seed:empty` | 貸出可能なノートPCを 0 件にして作り直す(E-07 の確認用) |
| `npm run db` | devices・lendings・lending_requests の中身を表示 |
| `npm test` | 洗い出し表の項目に対応した自動テスト(下記 2.) |

操作者の切り替えは `/login?user_id=○` を開く(ログイン機能は範囲外のため Cookie で代用。Gate1 と同じ)。

- 「洗い出し No」をテスト名に付けて対応づけ(例:`No.12 同じ端末を 2 人が確定`)
- 日またぎ(23:50 に確認 → 0:05 に確定)は時計を差し替えて再現

### 実装しなかったこと・注意点

| 内容 | 理由 |
|---|---|
| 修理・廃棄の操作画面 | 仕様(2. 11.)で範囲外。遷移の判定だけ実装 |
| 管理者による代行返却 | 元仕様に管理者が出てこない(確認事項 #7) |
| 台帳に残っている二重貸出データ(PC-0007・PC-0015)の是正 | どちらが正しい借用者か台帳から判断できない(確認事項 #8)。シードには含めていない |
| 退職・休職者が持ったままの端末の回収(台帳 L-024) | 人事・総務の回収フローの問題で範囲外 |
| 本物のログイン | Cookie の `user_id` で代用(Gate1 と同じ)。Cookie 自体の改ざんは防げない。リクエスト本文の user_id を無視する対策(No.38)のみ |
| CSRF 対策 | 洗い出しに入れておらず未対応 |
| 複数プロセスでの同時実行の自動テスト | `npm test` の同時実行テストは 1 つの Node プロセス内で行うため、リクエストが順番に処理される。別プロセス・別接続の競合は「ロックのタイムアウト(No.35)」と「部分ユニーク索引に直接 INSERT(No.12/15)」のテストで補っている |
| 仕様書にない表示 | 申請画面の入力欄の下の補助文(「明日から14日以内(土日は不可)」「100文字以内」)は入力補助として追加(優先度:低の範囲) |

動作確認専用のスイッチ:`FAIL_TX=1 npm start`(Windows PowerShell は `$env:FAIL_TX=1; npm start`)で、貸出・返却の 2 つ目の更新の前に意図的に失敗させる(No.33・34 の確認用)。`FAKE_NOW=2026-04-10T10:00:00+09:00` で現在時刻を固定できる。

## 5. 振り返り

### 5-1. 自分の洗い出しで、項目が 0 件だった観点カテゴリはどれですか。

0 件の観点は無かった(8 観点すべて 3 件以上)。ただし、**観点シートを使って埋めたから 0 件にならなかった**。シートが無い状態で「思いつくまま」に出していたら、④入力値と①在庫・状態に偏り、③重複・多重(No.12〜15)・⑥時間(No.29〜32)・⑧不正操作(No.37〜39)は薄くなっていたと思う。

### 5-2. 「言われれば当たり前」だったのに気づけなかった項目を 3 つ挙げ、なぜ自力で気づけなかったかを書いてください。

【要修正】以下は AI が作成した下書き。自分の言葉で書き直すこと(この行は提出前に削除)

1. **確定時にも全部の検証をやり直す(R-14)。** 画面でチェックしたからサーバー側は不要、と無意識に考えていた。確認画面を出したあとに状態が変わる(他の人が借りる・日付が変わる)ことは、画面を「見ている」だけでは出てこない。
2. **「戻る」と「確定」の再実行(No.14)。** 正常系は一方向にしか進まないと思い込み、利用者がブラウザバックで戻ることを考えていなかった。
3. **台帳の中にすでに実害が入っていること。** 仕様書だけを読んで洗い出そうとしていたが、配布された台帳の PC-0007・PC-0015 の 2 件の貸出や、休職中の E-1090 への貸出は、まさに例外系が起きた結果だった。データを「見る」と仕様の穴が見える。

### 5-3. Gate1 の振り返りで書いた「確認しに行くこと」リストと比べて、増えた観点は何ですか。

【要修正】以下は AI が作成した下書き。自分の言葉で書き直すこと(この行は提出前に削除)

Gate1 のリストは「権限」「状態遷移」「トランザクション」「排他制御(updated_at)」「メッセージ文言」が中心だった。Gate5 で増えたのは次の観点。

- **重複・多重**:連打、ブラウザバック、複数タブ、2 人同時(排他制御は Gate1 にもあったが、「同じ操作を 2 回」は無かった)
- **時間**:延滞、期限当日の境界、日付をまたぐ瞬間、時刻の基準(サーバーか端末か)
- **不正操作**:確認画面のスキップ、リクエスト値の書き換え、他人の ID
- **失敗時の画面**:ロールバックしたあと、利用者に何と見せるか(Gate1 は文言を足さなかった)
- **既存データを見る**:台帳から実害を読み取り、仕様の抜けを探す
- **優先度**:データが壊れるものから作る。全部を作ろうとしない
